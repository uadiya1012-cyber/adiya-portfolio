Vega A local, bilingual AI agent — and the shared "Brain" behind my AI tools

Vega is a Python agent that runs entirely on a MacBook: chat in Mongolian or English, a permission-gated coding agent, a hybrid RAG knowledge base and a news writer, all on local Ollama models. Its Brain module turns an Obsidian vault into shared memory that Claude Code, Claude Desktop, Antigravity and Gemini all read and write through one MCP server.

The problem

Cloud assistants are weak in Mongolian, bill per token and cannot see local files. And every AI tool I use keeps its own memory, so nothing learned in one is known to the next. I wanted a local-first agent whose permissions I control, and one place where all of my tools remember things.

What I built

  • Coding agent with a workspace sandbox. Tools are tiered read / write / exec: writes need one approval per session, commands need approval every time. Path escapes and secret files (.env, keys, .ssh) are refused. After an edit the agent shows the diff and runs the tests.
  • Hybrid retrieval. bge-m3 dense vectors plus SQLite FTS5 keyword search, article-aware chunking, and score thresholds set from measurements rather than defaults.
  • Model routing per task. gemma3:12b for Mongolian long-form writing, qwen3:8b for tool calling — one warm model at a time inside the 16 GB budget.
  • Mongolian quality guard. Heuristics catch broken Mongolian and CJK leakage and regenerate the answer.
  • Providers. Local Ollama or any OpenAI-compatible API, switchable per request.
  • The Brain. An Obsidian vault as shared memory. An MCP server exposes search, read, write, log, recent and a task board; privacy rules by front matter, tag or folder decide what cloud AIs may see.
  • Activity trail. Each day's work is written to the vault from four sources — Claude Code hooks, Antigravity's local database, git and Vega itself — by a nightly launchd job. A morning brief is injected into every new Claude Code session.
  • Task board with a human in charge. An AI may propose a task and report progress, but only the human can close it.

Hard problems and decisions

Adding a tool made the other tools worse

The eval showed it plainly: after adding a task-board tool, tool selection on an 8B model dropped from 40/40 to 36/40. Offering every tool on every turn was the mistake. Now the task tool is offered only when the message is about tasks, and every new tool must pass both the eval and real runs before it ships. The suite stands at 46/46.

The fine-tune that lied

A LoRA model trained on my own Mongolian data produced gibberish in use while its metrics looked fine. The training set contained 21 duplicated pairs that had leaked from the test set. The fix was a data audit and routing everything back to the base model; fine-tuning is on hold until there is a clean dataset and more memory.

Embeddings that actually separate Mongolian topics

nomic-embed-text scored every Mongolian passage above 0.7 against every query, so no threshold could tell relevant from irrelevant. bge-m3 separates topics: relevant answers score 0.54–0.74, unrelated ones stay at or below 0.52. Thresholds are set from those measurements and re-measured as the corpus grows.

Visibility over blocking

Rather than locking AI tools down, every action they take is written to the day's note with an "auto" tag, and the permission model is "read freely, ask before changing". A daily health line lists where work sits uncommitted or unpushed.

One memory, no copies

Claude Code keeps its memory in per-project folders. Those folders are now symlinks into the vault, so there is a single source of truth. The indexer walks the vault without following links — a small detail that decides where the real files must live.

What I learned

  • Evaluate every prompt and tool change; small models regress silently.
  • Never trust a metric without auditing the data behind it.
  • On a laptop, memory budgeting is a feature: one warm model, a fixed context window, explicit keep-alive.
