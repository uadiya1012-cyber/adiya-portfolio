AutoHub A roadside car-repair marketplace with live dispatch

Customers request a mechanic wherever they are. The platform picks the best available mechanic by distance, rating and current load, walks each booking through a strict state machine, tracks the job live over WebSocket and settles with QPay. FastAPI and PostGIS on the backend; a React PWA and a native Expo app on one shared TypeScript client.

The problem

A breakdown on the road today means phone calls and guesswork: who is nearby, who is free, who is any good, and where is the mechanic right now? The client wanted a marketplace that answers those questions automatically and keeps a history for each vehicle.

What I built

  • Dispatch. PostGIS finds mechanics within range; each candidate is scored and ranked, and the winner is assigned.
  • Booking state machine. Seven statuses with an explicit allow-list of transitions and of who may perform each one.
  • Live tracking. A realtime hub (in-memory for a single node, Redis-backed for many) pushes status and position updates over WebSocket to the customer and the dispatcher.
  • Payments and reviews. QPay invoices with their own status lifecycle, a pricing service and mechanic reviews.
  • Vehicles. A registry with a lookup layer for the national transport centre — simulated today behind a protocol so the real API can be dropped in later.
  • Parts delivery. A delivery status flow for spare parts brought by a taxi partner.
  • Rate limiting. A Redis sliding-window log implemented as an atomic Lua script.
  • Two front-ends, one client. A React PWA and a native Expo app (iOS and Android) share packages/shared for types and the API client.

Hard problems and decisions

Dispatch you can explain

Candidates are filtered by radius and availability in PostGIS, then scored: 50 % distance (a reference-distance decay, so the first kilometres matter most), 30 % rating and 20 % free capacity (1 − active jobs ÷ capacity). The weights are named constants with the reasoning written next to them, so the client can tune them without touching the algorithm.

A booking cannot go backwards

The earlier API accepted any string as a status, so a completed job could be reopened. Transitions are now an explicit allow-list: pending → confirmed → assigned → en route → in progress → completed. Cancellation is allowed only before work starts, and each transition is restricted to the roles that may perform it. Everything else is rejected instead of silently "fixed".

Layers with a direction

api → services → repositories → db. Routers never write SQL; repositories never make business decisions. This made the external registry integration a one-function swap: the simulated client sits behind a protocol, and the real one replaces it without touching the rest of the code.

One client for two front-ends

The web PWA and the native Expo app import the same shared package. Adding mobile did not mean rewriting the API client; only the token storage strategy differs between the two.

Rate limiting that is actually atomic

The sliding-window log runs as a Lua script inside Redis, so check-and-record happens in one step even under concurrent load.

What I learned

  • Make the algorithm legible to the client; named weights beat clever formulas.
  • An allow-list state machine removes a whole class of "impossible" bugs.
  • Design the integration seam before the partner API exists; the swap is then trivial.
